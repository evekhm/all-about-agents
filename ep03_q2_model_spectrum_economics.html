Open-Weight vs. Proprietary Models Across the Full Model Spectrum

Choosing between open-weight models, managed proprietary APIs, distilled small models, and classical machine learning by applying constraints, serving physics, and task evaluations in order.

In this episode, we move past the false binary of "open source versus closed APIs" to build a constraint-first framework for model selection. We separate open-weight, open-source, and proprietary models, clear up enterprise privacy and Zero Data Retention boundaries, work through GPU VRAM and utilization math, and map workloads across a five-tier hybrid router.

Next in Episode 03: Question 03 · Production Retail Demand Forecasting and Honest LLM Scoping (or view the 5-Question Master Cheat Sheet).

Teams often treat model choice as a binary debate between "open source" and "closed APIs," or pick one flagship frontier model from a public leaderboard and route every request through it. Public leaderboards measure generic chat distributions, whereas production decisions depend on the customer's specific extraction or compliance workload. Sending high-volume routine tasks to a heavy reasoning model inflates latency and token spend several times over. Conversely, spinning up dedicated GPU clusters for an open-weight model to "save money or protect privacy" frequently costs more than a managed enterprise API once idle nighttime GPU hours and engineering maintenance are counted.

1. What Actually Separates Open-Weight, Open-Source, and Proprietary Models

Ambiguous terminology causes legal, security, and platform stakeholders to talk past one another when evaluating model options.

Distinguish three precise release models (Table 1 in Section 3 then compares the three ways to consume them across six dimensions):

  • Proprietary / Closed Managed Models (such as Gemini Pro / Flash / Flash-Lite, Claude Opus / Sonnet / Haiku, OpenAI GPT models): Weights stay private behind a provider-managed endpoint. You consume tokens over an API with elastic capacity, built-in context caching, and zero GPU cluster operations, while accepting vendor model-deprecation calendars that require regression testing when versions rotate.
  • Open-Weight Models (such as Google Gemma 4, Alibaba Qwen3, DeepSeek-R1 / V3, OpenAI gpt-oss under permissive Apache 2.0 or MIT licenses, and Meta Llama under community licenses with monthly-active-user commercial thresholds): Trained weight tensors are downloadable so you can inspect tokenization, freeze an exact SHA-256 checkpoint for multi-year regulated reproducibility, attach custom classification heads or multi-tenant LoRA adapters, run reinforcement learning with verifiable rewards (RLVR), or deploy inside disconnected environments. Training corpora and data recipes remain unpublished.
  • Fully Open-Source Models (such as OLMo or Pythia): Publish weights, training code, and full pretraining datasets for scientific auditability, usually trailing frontier capability by a generation.

2. Clearing Up the Enterprise Privacy Boundary

Stakeholders frequently conflate consumer chat web apps with enterprise cloud model APIs and assume self-hosting open weights is the only way to keep proprietary data private.

On enterprise cloud platforms (such as Google Cloud's Agent Platform), contractual terms prohibit using customer prompts, responses, tuning data, or tuned weights to train foundation models (Google Cloud, 2026). Traffic stays inside Private Service Connect and VPC Service Controls perimeters, regional endpoints enforce geographic data residency, customer-managed encryption keys (CMEK) control storage and tuned adapters, and configuring Zero Data Retention (disabling abuse-monitoring prompt logs, request-response logging, consumer web-search grounding, and stateful disk persistence) eliminates prompt retention at rest. Self-hosted open weights become mandatory for governance in three specific situations: physically air-gapped sovereign or defense networks, regulatory audits requiring immutable frozen weights with zero vendor version rotation, and countries lacking a local managed cloud region.

3. Serving Physics and Total Cost of Ownership (Why Utilization Decides Economics)

Comparing raw per-million-token API prices against hourly GPU rental prices ignores KV-cache memory limits, prefill-versus-decode hardware bottlenecks, and diurnal enterprise traffic curves.

Self-hosting a model requires sizing GPU memory (VRAM) for both static weights and live concurrent user context:

GPU Memory & Latency Physics for Self-Hosted Open Weights
# 1. Total VRAM must hold weights + live KV cache + runtime (~2 GB)
Weight_Bytes      = Parameters * Bytes_Per_Param          # e.g., 12B at 8-bit = ~12 GB
KV_Bytes_Per_Tok  = 2 * Bytes_Per_Value * n_layers * n_kv_heads * d_head  # GQA shrinks n_kv_heads; MLA compresses KV into a latent

# Worked check on 1x NVIDIA L4 (24 GB VRAM, ~300 GB/s bandwidth):
# 24 GB - 12 GB (weights) - 2 GB (runtime) = ~10 GB left for KV cache
# At ~100 KB/token (BF16), 10 GB holds ~100K live tokens (~25 concurrent users at 4K context).

# 2. Prefill (Time to First Token) is compute-bound; Decode (per output token) is bandwidth-bound
TTFT_seconds      ≈ (2 * Active_Params * Prompt_Tokens) / (GPU_TFLOPS * MFU)
TPOT_seconds      ≈ Active_Weight_Bytes_Read / Memory_Bandwidth   # why APIs price output ~4–8x input

Sparse Mixture-of-Experts (MoE) open models (such as a 26B total / 4B active parameter architecture) require VRAM for all 26B parameters while reading only ~4B active weights per generated token, giving small-model decode speed once fitted into GPU memory. Even with fast engines like vLLM (PagedAttention, continuous batching, prefix caching) and KV-cache-aware load balancers, dedicated GPUs bill 24 hours a day. Enterprise internal workflows typically send 70%–80% of daily traffic during daytime business hours and sit nearly idle overnight and on weekends. Meanwhile, constant-capability managed token prices have fallen roughly 10x per year (a16z LLMflation, Nov 2024). Consequently, before provisioning GPUs, teams pull managed FinOps levers first: model routing, prefix context caching (up to 90% off cached input), batch APIs (50% off), per-step thinking budgets, and Provisioned Throughput for the steady baseline floor. Dedicated open-weight GPUs win economically when sustained 24/7 GPU utilization exceeds ~50%–65% (or when a compact 2B–12B model runs on scale-to-zero serverless GPUs).

4. Navigating All Five Tiers with a Tunable Hybrid Router

No single tier optimizes latency, accuracy, and unit economics across every step of an application.

Mature production architectures combine models across five distinct tiers (Table 2), assigning each workflow step statically first and escalating dynamically on ambiguous turns:

Table 2 · The Five-Tier Production Model Spectrum and When to Use Each Tier
Spectrum Tier Representative Models Latency & Cost Primary Production Use Cases
Tier 0 Classical ML, Time-Series FMs & Solvers LightGBM, XGBoost, TimesFM, OR-Tools, BM25 / bi-encoders 1–15 ms · pennies per million predictions Tabular demand/churn prediction, anomaly scoring, routing math, first-stage retrieval
Tier 1 Distilled SLMs & Fast Scorers (2B–12B) Fine-tuned Gemma 4 E4B / 12B, Qwen 4B–9B, cross-encoder rerankers 50–250 ms · single L4 GPU High-QPS intent routing, PII redaction, rubric guardrails, top-40 passage reranking
Tier 2 Managed Workhorse Models Gemini Flash / Flash-Lite, Claude Haiku, small OpenAI GPT tier 0.4–2.0 s · low per-token + 90% cache discount 80%–90% of enterprise GenAI: structured JSON extraction, grounded RAG answers, summarization
Tier 3 Open-Weight Mid / Large (26B–671B) Gemma 4 26B-A4B / 31B, Llama, Qwen3, DeepSeek-R1/V3 MaaS per-token or multi-GPU H100/H200 Air-gapped deployments, frozen regulated weights, custom RL/LoRA, steady 24/7 batch pipelines
Tier 4 Frontier Reasoning Models Gemini Pro, Claude Opus / Sonnet, deep-thinking models 3–20+ s · highest per-token compute Hardest 2%–15% escalations, complex multi-doc synthesis, golden-eval grading & teacher distillation

Two practical rules keep hybrid routing honest in production. First, optimize cost per resolved task alongside per-token price: on multi-step tool loops, a model that costs one-third as much per token while taking four times as many retry turns and failing more often raises total cost. Second, keep each multi-turn session within two to three model tiers; bouncing a conversation across four or five different model endpoints forfeits prefix-cache hits at every provider and multiplies prefill token spend.

Takeaway: Filter by hard governance constraints first, compare optimized pay-per-token costs against 24/7 GPU utilization second, and combine classical ML, workhorse models, and frontier escalations via a 2-to-3-tier router.
