Building a Lean, Domain-Specific Agent

Equipping one lean agent with the specialized capabilities required to understand domain terminology, navigate cross-referenced rules, and handle conflicting information using minimal components.

In this episode, we bring trust controls, model selection, and modern retrieval together to build a lean, domain-specific agent. Starting from a single-agent whiteboard sketch, we harden five policy-specific seams—compiled whole-section RAG, auto-injected defined terms, parameterized DB lookups, deterministic precedence, and verbatim-quote verification—then trace a prior-authorization request and an ADK 2.x workflow.

Review all five topics side by side in the 5-Question Master Cheat Sheet.

Suppose an enterprise asks us to build a domain-specific agent for a vertical workflow such as policy and prior-authorization verification: evaluating incoming requests against hundreds of domain rulebooks, Master Services Agreements (MSAs), signed addenda, and regional regulations. Three core design questions test whether we know how to turn a generic model into a reliable domain specialist: how we make the agent understand specialized domain terminology and cross-references, how we handle conflicting rules across sources, and how we keep the component count minimal. The examples below move between contract language and healthcare prior authorization, since both rely on the same mechanics.

1. Starting from a Clean Single-Agent Whiteboard Sketch

Figure 1 shows a first whiteboard sketch: place an Ingress + Guard and Gateway + Safety Screening layer in front of one LLM Agent, connect that agent to three knowledge sources (a DB, RAG, and a SKILL.md file for policy rules and terminology), pass its structured output (status: ok / fail, confidence, resources) through an egress gateway into a Verify Using Code gate, and escalate uncertain cases to HITL.

Figure 1 — Initial single-agent whiteboard sketch: the sketch has the right instinct to keep one LLM agent behind ingress/gateway guards and verify structured output in code, and it leaves five policy-specific seams open under close inspection.
Code guard / verifier Gateway screen Single LLM agent Human escalation

That initial sketch already gets the four most important structural choices right: it avoids multi-agent swarm sprawl by starting with a single agent, screens inputs and outputs at a gateway boundary, recognizes that domain terminology needs explicit representation alongside retrieval and structured records, and puts deterministic code verification ahead of human escalation. Pressure-testing every arrow on Figure 1 then exposes five policy seams whose fixes turn that sketch into a production-ready policy engine (Figure 2):

  1. Optional SKILL.md lookup vs. automatic per-contract <defined_terms> injection: Keep global review instructions in SKILL.md, while moving contract-specific Defined Terms into an indexed glossary injected automatically in code, since a model seeing an everyday English word like "Affiliate" or "Customer" assumes it knows the meaning and skips calling a terminology file, and a flat Markdown file covering hundreds of contracts outgrows the agent's file-read limit.
  2. Generic RAG box vs. an Offline Policy Compiler: Compile section trees, table headers, effective_date scope, and 1-hop cross-references deterministically before runtime so "Notwithstanding Section 4.2, see Schedule B" never arrives cut in half.
  3. Direct LLM Agent → DB arrow vs. parameterized read-only tools + intake quarantine: Front the database with typed, read-only parameterized queries scoped to the caller/tenant (Episode 01), and parse untrusted uploaded claim text in a toolless step first.
  4. Self-reported model confidence float vs. quote checks + precedence code + CONFLICT_ESCALATE: Generative models frequently emit confidence = 0.95 while hallucinating or guessing across contradictory rules; replace raw float trust with server-checked verbatim quotes, deterministic authority_tier precedence in code, and an explicit CONFLICT_ESCALATE status for same-tier contradictions. A model-reported clarity score is kept as a one-way floor: a low value sends the case to HITL, and approval still rests on verified quotes.
  5. Single exit to HITL vs. three-way exit + Audit Store: Split the exit of Verify Using Code three ways: clean verified approvals write an immutable AdjudicationRecord, missing evidence returns a checklist to the requester, and denials, conflicts, missing referenced schedules, and low-clarity cases route to HITL.

2. Making the Agent Understand Specialized Domain Language and Cross-References

Legal and regulatory prose breaks standard semantic chunking in four specific ways. First, capitalized Defined Terms (such as "Affiliate", "Customer Data", "Permitted Subprocessor", or "Material Adverse Effect") carry bespoke definitions in Section 1 or a separate Glossary that routinely narrow or invert ordinary dictionary meanings; LegalBench treats this kind of interpretation as a task category of its own (Guha et al., NeurIPS 2023). Second, cross-references and carve-outs split a single logical rule across distant sections or external schedules ("Notwithstanding Section 4.2, and subject to Exhibit B..."); reading Section 4.2 alone produces the exact opposite verdict. Third, effective dates and jurisdictional scope mean two 98%-similar policy versions coexist in storage while only one was legally in force on the event date. Fourth, numeric thresholds and code ranges ("Applies to procedure codes 10000–69999" or embedded fee tables) never match literal token queries for 10021 unless parsed structurally.

Solve document structure once at ingestion time using an Offline Deterministic Policy Compiler (zero LLM chunking calls), paired with structured context assembly at runtime:

  • 100%-Coverage Structural Clause & Table Parsing: Parse native .docx XML and PDF layout into intact numbered clauses carrying full heading breadcrumbs (MSA > Art. 8 Liability > 8.4 Data Breach Carve-Out), repeat column headers on every split table block, and index numeric/code ranges for exact bounds checking. Block import automatically if any line of raw text is dropped.
  • Automatic Defined-Terms Glossary Injection: Extract every defined term and its verbatim definition into a deterministic lookup dictionary per document family. At runtime, scan each routed policy clause in code (using fast exact lexical / Aho-Corasick matching) and automatically prepend a read-only <defined_terms> block containing the exact contractual definitions of every capitalized term used in that clause.
  • Pre-Linked Cross-Reference Graph + Missing-Attachment Gate: Resolve internal section pointers (Section 8.4(b), scoped per part/chapter) and cross-policy titles (Information Security Addendum) into explicit graph edges during compilation. At runtime, hydrate 1-hop cited passages alongside the primary policy. Record any reference whose target file is absent from the repository in an explicit unresolved_references field so the runtime fails closed with MISSING_REFERENCED_DOC.
  • Atomic Predicate Evaluation with Verbatim Quotes: Ask the model to evaluate each applicable rule as a structured checklist item (PASS, FAIL, MISSING_EVIDENCE, NOT_APPLICABLE, DEFERRED_TO_LINK, or CONFLICT_ESCALATE) accompanied by the exact verbatim sentence from the policy, which Python code verifies against the source text.

3. Dealing with Conflicting Information: Precedence Code vs. Human Escalation

When one document states "Vendor invoices are payable Net-30" and another states "Vendor invoices are payable Net-60," or a global policy permits cloud backups in any region while a German addendum restricts storage to Frankfurt, letting a language model "weigh both sides and pick the most reasonable answer" creates silent legal liability.

Separate policy conflicts into two distinct categories: resolvable hierarchy overrides handled deterministically in code, and genuine equal-rank ambiguities escalated directly to a human reviewer (Table 1):

1. Temporal Supersession
(2024 Policy vs. 2026 Policy)		 Lex Posterior (active version on event date governs) Plain Code (Pre-filter) Scope query filters effective_start <= event_date <= effective_end and excludes records marked superseded_by before any LLM call runs.
2. Authority Tier Override
(Signed SOW / Statute vs. Global MSA)		 Lex Superior / Order-of-Precedence clause Plain Code (Precedence Merger) Every doc carries explicit authority_tier (1: Statute > 2: Signed Amendment/SOW > 3: MSA > 4: Regional Policy > 5: Global Baseline). Higher rank wins in code and logs overridden_clause_id.
3. Specific Carve-Out vs. General Rule
("Notwithstanding Sec 4.2...")		 Lex Specialis (specific exception narrows baseline) Whole-Section Hydration + Policy LLM Agent Whole-section retrieval + 1-hop cross-reference hydration keeps the carve-out attached to the general clause in one evaluation window.
4. Conjunctive Safety / Compliance Rules
(Security Gate + Privacy Gate)		 All mandatory gates must pass Plain Code (Severity Lattice) Independent domain checks merge via strict lattice: FAIL > CONFLICT_ESCALATE > MISSING_EVIDENCE > PASS > NOT_APPLICABLE; DEFERRED_TO_LINK is resolved by the one bounded hop before the merge.
5. Equal-Rank Contradiction or Missing Schedule
(Two active Tier-2 Addenda disagree)		 Genuine legal ambiguity Human Legal / Compliance Reviewer Code detects two opposing verdicts at identical authority_tier (or non-empty unresolved_references), emits CONFLICT_ESCALATE, and presents both verbatim quotes side by side.

4. How Many Agents Do We Need? Keeping the Single-Agent Spine

A frequent first design is a conversational swarm of five to eight specialized agents (such as separate Definitions, Statute, Contract, Debate, and Summary agents) chatting in a shared thread. In practice, multi-agent chat swarms multiply latency and token cost, break KV prefix caching, paraphrase away critical legal modal verbs (turning "shall" into "should" across handoffs), and produce non-reproducible audit trails (Anthropic, Dec 2024; Google Cloud, Nov 2026; Episode 02).

Keep the exact single-agent spine from Figure 1 inside one deterministic workflow service, growing it in place into Figure 2:

  1. Ingress + Guard + Agent Gateway & Model Armor: Authenticates the caller, filters active policy scope by effective_date and jurisdiction, screens inputs for prompt injection via Model Armor, and (whenever intake arrives as raw unstructured prose) runs a single toolless CaseFacts extraction pass. When intake arrives from a structured form or API, that extra parse disappears completely, leaving just one LLM role in the entire architecture.
  2. Hardened Three-Source Context Assembly (DB via MCP Tool + Compiled RAG + SKILL.md / Glossary): Parameterized read-only SQL fetches live customer or claim records under tenant row ACLs; Compiled RAG loads the active whole policy sections and 1-hop cited clauses; SKILL.md supplies the global review rubric while plain code automatically injects the per-contract <defined_terms> block.
  3. Single Policy LLM Agent + Egress Gateway Screen: Evaluates CaseFacts against each routed policy in a clean single turn (0 write tools, include_contents="none"), and emits the typed Status & Resources schema with verbatim_quote placed ahead of status (PASS, FAIL, MISSING_EVIDENCE, NOT_APPLICABLE, DEFERRED_TO_LINK, or CONFLICT_ESCALATE), which then passes through egress Model Armor.
  4. Verify Using Code → Three-Way Exit (Immutable Audit Store, Pend for Evidence, HITL Domain Escalation): Plain Python checks that every verbatim_quote appears in the source policy text, follows at most one bounded DEFERRED_TO_LINK hop, applies deterministic authority_tier precedence (Statute > Signed SOW/Addendum > MSA > Global), writes clean approvals to the Immutable Audit Store, returns a checklist to the requester on MISSING_EVIDENCE, and routes denials (FAIL), CONFLICT_ESCALATE, MISSING_REFERENCED_DOC, or low-clarity cases to HITL Domain Escalation. Code raises CONFLICT_ESCALATE itself when two findings at the same authority_tier disagree, alongside any conflict the agent flags inside a single policy.

5. Worked Example: How RAG Drives a Prior Authorization Check

To see what Compiled RAG actually does step by step, trace a single prior authorization request: a clinic requests a lumbar spine MRI (CPT 72148) for a patient on a Texas PPO plan (service_date = 2026-11-15), attaching a short clinical note ("low back pain for 3 weeks, tried ibuprofen", with the neurological exam page omitted). We need to answer two exact questions: does the request comply with the governing policy, and is there enough supporting clinical evidence attached?

  1. Extract Structured Request & Chart Facts (Ingress + Intake Parse): Parse the form and clinical note into a compact CaseFacts object containing the coded identifiers (cpt_code = "72148", plan = "TX_PPO", service_date = "2026-11-15") alongside the documented clinical facts (pain_weeks = 3, therapies = ["ibuprofen"], neuro_exam_attached = false). Meanwhile, DB via MCP Tool confirms active member eligibility.
  2. Filter Active Policy Scope First (Plain Code): Before computing any similarity score, restrict the search index to policies where plan == "TX_PPO" and effective_start <= 2026-11-15 <= effective_end. Expired 2024 rules and Medicare policies never enter retrieval.
  3. Run Hybrid Code + Indication Search (Compiled RAG): Query the scoped policies using exact/range lookup on CPT 72148 (matching Musculoskeletal Imaging Policy MSK-04, which covers 72141–72158) combined with BM25 + dense vector + reranking on the clinical indication ("lumbar MRI uncomplicated low back pain").
  4. Hydrate the Complete Criterion Tree, Linked Addendum, and Defined Terms (Code Context Builder): Return the entire governing section of MSK-04 so its AND / OR criteria and red-flag exceptions stay attached: "Approve lumbar MRI when EITHER (a) failed Conservative Therapy is documented OR (b) progressive neurological deficit is documented on exam." Automatically pull any 1-hop linked addendum (TX-Mandate-2026) and inject <defined_terms> from the glossary ("Conservative Therapy: physician-supervised physical therapy across >= 6 weeks; over-the-counter NSAIDs alone do not satisfy this requirement").
  5. Evaluate Criterion by Criterion with Evidence Status (Single Policy LLM Agent): Guided by SKILL.md, the agent checks the chart facts against each criterion separately, quoting the exact policy rule first and distinguishing a failed rule from missing chart paperwork: Criterion (a) evaluates to FAIL (3 weeks of ibuprofen vs. 6 weeks of supervised physical therapy), while Criterion (b) evaluates to MISSING_EVIDENCE (the neurological exam page was omitted).
  6. Verify Quotes, Apply Precedence, and Route Asymmetric Outcomes (Verify Using Code): Python verifies that every quoted rule exists verbatim inside MSK-04, applies authority_tier precedence if TX-Mandate-2026 modifies MSK-04, and routes by outcome: all-criteria PASS with verified chart spans logs an approval to the Immutable Audit Store; MISSING_EVIDENCE sends a targeted checklist back to the clinic naming the missing neurological exam; clinical denials (FAIL) and same-tier policy conflicts (CONFLICT_ESCALATE) route to HITL clinical review with highlighted quotes side by side. Here criterion (a) fails on the chart as submitted, and because the two criteria are joined by OR, the open criterion (b) can still approve the request, so the case pends for evidence ahead of any denial.

6. Implementation Sketch: Domain-Specific Policy Agent Workflow in ADK 2.x

The ADK 2.x graph below follows Figure 2: ingress_and_guard handles scope filtering, parameterized read-only DB lookup, compiled RAG hydration, and automatic <defined_terms> injection alongside SKILL.md; single_policy_agent runs behind ingress and egress Model Armor callbacks (mode="single_turn", include_contents="none", strict Pydantic output_schema); and verify_using_code checks verbatim quotes in Python, applies authority_tier precedence, and splits between write_audit_decision_record, request_missing_evidence, and escalate_to_hitl. The bounded DEFERRED_TO_LINK hop and the helper functions are left out for brevity.

Hardened single-agent policy workflow in ADK 2.x matching Figure 2 (verified against google-adk 2.14)
from pathlib import Path
from typing import Literal
from pydantic import BaseModel, Field
from google.adk import Agent, Context, Event, Workflow

POLICY_REVIEW_SKILL_MD: str = Path("skills/policy_review/SKILL.md").read_text(encoding="utf-8")


class CaseFacts(BaseModel):  # generic intake; prior-auth maps request_id, service_date, plan, cpt_code onto these
    case_id: str
    event_date: str
    jurisdiction: str
    codes: list[str] = Field(default_factory=list)
    summary_facts: str


class ClauseFinding(BaseModel):
    verbatim_quote: str = Field(description="Exact sentence copied from policy text first.")
    resource_doc_id: str
    clause_id: str
    authority_tier: int = Field(ge=1, le=5)
    clarity_score: float = Field(ge=0.0, le=1.0)  # escalation floor; approval still needs verified quotes
    status: Literal["PASS", "FAIL", "MISSING_EVIDENCE", "NOT_APPLICABLE", "DEFERRED_TO_LINK", "CONFLICT_ESCALATE"]


class StatusAndResources(BaseModel):
    findings: list[ClauseFinding]


single_policy_agent: Agent = Agent(      # Central Policy LLM Agent from Figure 1 & 5B
    name="single_policy_agent",
    model="gemini-3.8-flash",
    mode="single_turn",
    include_contents="none",
    before_model_callback=model_armor_ingress_screen,   # Agent Gateway / Model Armor ingress
    after_model_callback=model_armor_egress_screen,     # Agent Gateway / Model Armor egress
    output_schema=StatusAndResources,
    instruction=(
        f"{POLICY_REVIEW_SKILL_MD}\n"
        "Evaluate CaseFacts against the compiled RAG sections, read-only DB facts, and "
        "auto-injected <defined_terms>. Copy verbatim_quote before setting status."
    ),
)


def ingress_and_guard(ctx: Context, facts: CaseFacts) -> Event:
    db_row: dict = query_parameterized_readonly_db(facts.case_id, ctx.state["tenant_id"])
    rag_bundle: dict = load_compiled_rag_and_defined_terms(facts) # date + tier + 1-hop links
    if rag_bundle["unresolved_references"]:
        return Event(route="HITL", output={"reason": "MISSING_REFERENCED_DOC"})
    ctx.state["rag_bundle"] = rag_bundle
    return Event(route="EVALUATE", output={"facts": facts, "db": db_row, "rag": rag_bundle})


def verify_using_code(ctx: Context, verdict: StatusAndResources) -> Event:
    sources: dict[str, str] = ctx.state["rag_bundle"]["source_texts"]
    for f in verdict.findings:
        if not alphanumeric_span_exists(f.verbatim_quote, sources.get(f.resource_doc_id, "")):
            return Event(route="HITL", output={"reason": "UNVERIFIED_QUOTE"})
        if f.clarity_score < 0.75:
            return Event(route="HITL", output={"reason": "LOW_CLARITY"})
    merged: dict = merge_by_authority_tier(verdict.findings)      # Statute(1) > SOW(2) > MSA(3)
    if merged["has_same_tier_conflict"]:               # includes agent-flagged CONFLICT_ESCALATE
        return Event(route="HITL", output=merged)
    if merged["status"] == "FAIL":                     # status applies the AND / OR criterion tree; denials get human review
        return Event(route="HITL", output=merged)
    if merged["status"] == "MISSING_EVIDENCE":
        return Event(route="PEND_FOR_EVIDENCE", output=merged)
    return Event(route="AUDIT_RECORD", output=merged)


policy_workflow: Workflow = Workflow(
    name="hardened_single_agent_policy_engine",
    edges=[
        ("START", ingress_and_guard),
        (ingress_and_guard, {
            "EVALUATE": single_policy_agent,
            "HITL": escalate_to_hitl,
        }),
        (single_policy_agent, verify_using_code),
        (verify_using_code, {
            "AUDIT_RECORD": write_audit_decision_record,
            "PEND_FOR_EVIDENCE": request_missing_evidence,
            "HITL": escalate_to_hitl,
        }),
    ],
)
